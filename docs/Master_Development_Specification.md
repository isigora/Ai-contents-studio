# Master Development Specification — Business Knowledge & Content Studio

**버전:** 1.0 · 2026-09-28  
**상태:** Work 개발 기준 문서 · 제품명은 임시로 `Content Studio`  
**대상:** 제품 책임자, 디자이너, Work 개발 에이전트

## 0. Work에 전달할 실행 지시

> 이 문서를 제품의 기준 명세로 사용하라. 먼저 현재 저장소와 `product-studio-mvp.zip`이 제공되었는지 확인하고, 있으면 코드를 검사한 뒤 재사용 가능한 기능만 가져와라. 목표는 여러 기업이 각각 자기 회사·제품·고객·증거를 저장하고 수정한 다음 목적별 콘텐츠를 생성·편집·보관하는 실제 작동 Web SaaS MVP다. 아래 **P0 완료 기준**에 맞춰 순서대로 구현하고, 매 단계에서 작동 화면과 테스트 결과를 보여라. 디자인은 Business X의 명료한 정보 위계와 목표 중심 탐색에서 영감을 얻되 상표, 로고, 문구, 화면을 복제하지 마라. 외부 게시·유료 AI 호출·결제는 명세의 승인 경계를 지켜라. 결정이 필요한 사항은 문서의 기본값을 사용하고, 진행을 막는 자격 증명·법적 요구·실제 운영 도메인만 한 번에 모아 질문하라. 미완성 기능을 작동한다고 표시하지 마라.

### 한 문장 정의

**기업이 검증된 제품 정보를 한곳에 축적하고, 원하는 고객·목표·채널에 맞춰 믿을 수 있는 소개 콘텐츠를 반복 제작하는 웹 작업공간.**

### 목적과 성공 신호

- 공급자: 회사 정보를 매번 다시 설명하지 않고 제품별 사실을 업데이트한다.
- 제작자: 고객과 목표를 선택해 글을 만들고 근거를 확인한 뒤 수정·저장한다.
- 수요자: 과장된 표현보다 관련성 높은 설명과 확인 가능한 증거를 접한다.
- 첫 사용 성공: 새로운 고객사가 가입해 제품 1개를 등록하고, 서로 다른 목적 2개로 초안을 생성해 저장하고, 제품 가격을 수정해 새 초안에 반영하는 데 장애가 없다.
- 장기 북극성: `공급자 지식 → 승인된 콘텐츠 → 배포 → 반응 → 학습 → 공급자/고객 AI 연결`. P0는 **지식과 콘텐츠 제작**까지다.

## 1. 범위와 우선순위

| 단계 | 반드시 동작할 기능 | 제외 또는 다음 단계 |
|---|---|---|
| **P0: 사용 가능한 MVP** | 가입·로그인, 기업 Workspace 생성·전환, 회사·브랜드·제품/서비스·고객·문제·가치·기능·증거·가격·CTA 등록/수정, 이미지/문서 자산 업로드, 목적별 글 초안 생성, 근거·누락 표시, 직접 편집, 버전 저장, 내보내기 | 외부 채널 자동 게시, 자동 성과 수집, 결제, 고객 AI 매칭, 생성형 동영상 |
| **P1: 제작 확장** | 승인 흐름, 채널별 템플릿, 보유 사진 기반 이미지 카드, 기초 영상/자막 내보내기, 한국어·중국어·영어 품질 개선, 콘텐츠 재사용 | X 등 계정 자동 연결은 별도 연동 검증 후 |
| **P2: 운영** | 공식 API를 통한 선택적 게시, 승인 후 예약, 사용량·성과 수집, 감사 기록·과금 | 채널별 API 정책·권한·비용 확인 전 구현 약속 금지 |
| **P3: 양방향 네트워크** | 구매자 동의에 따른 수요 표현·매칭·후속 분석 | 구매자 정보 공유 범위, 동의 및 매칭 품질을 별도 설계 |

초기 출시 언어는 **한국어 UI**, 콘텐츠 출력은 **한국어·简体中文·영어**. UI 다국어는 P1. PC에서 전체 기능, 휴대폰에서 정보 확인·간단 수정·초안 생성·승인 가능한 반응형 Web App. PWA 설치는 기본 기능이 안정된 뒤 추가한다.

## 2. 사용자와 핵심 여정

**역할:** `owner`(Workspace 관리), `editor`(정보·초안 편집), `viewer`(열람). P0는 owner 계정으로 전체 여정을 완성하고, 권한 모델은 처음부터 준비한다. 초대 UI는 P1이어도 서버의 권한 검사는 P0에 포함한다.

1. 가입 → Workspace 생성 → 회사명/업종/기본 언어 입력.
2. `내 비즈니스`에서 브랜드 목소리, 제품 또는 서비스, 고객군, 문제, 원하는 변화, 기능, 혜택, 근거와 자산 입력. 최소 필수값은 제품명, 대상 고객, 실제 제공 내용, CTA. 나머지는 누락 안내를 제공한다.
3. `콘텐츠 만들기`에서 **목표**(인지·이해·문의·구매 지원), 제품, 고객군, 채널, 언어, 톤, 길이, CTA 선택.
4. 시스템은 해당 Workspace의 사실만 조립 → 설득 구조 적용 → 초안과 사용한 근거 목록 생성. 근거 부족 시 주장 강도를 낮추거나 명확히 질문한다.
5. 사용자는 미리보기에서 수정 → 저장/버전 생성 → 복사 또는 파일 내보내기. 생성된 초안은 자동 게시되지 않는다.
6. 원천 정보가 바뀌면 기존 콘텐츠는 당시 버전으로 보존하고 `원천 정보 변경됨` 표시. 새 가격이 반영된 초안은 **명시적 재생성**으로 만든다. 게시 또는 승인된 기록을 조용히 덮어쓰지 않는다.

## 3. 제품 정보 모델

### 세 계층

1. **Fact:** 고객이 입력하거나 업로드한 사실. 가격, 날짜, 기능, 사용 조건에는 출처·확인 상태를 붙인다.
2. **Knowledge:** 대상 고객 ↔ 문제 ↔ 결과 ↔ 기능/혜택 ↔ 근거의 관계. AI 제안은 `suggested`, 사용자가 확인하면 `approved`.
3. **Content:** 목표·채널별 초안. 참조한 Fact/Knowledge 버전, 생성 설정, 편집 이력, 상태를 기록한다.

### 최소 엔터티와 관계

| 엔터티 | 핵심 필드 | 관계/규칙 |
|---|---|---|
| `workspace` | id, name, locale, created_at | 모든 비즈니스 데이터의 소유 단위 |
| `membership` | user_id, workspace_id, role | Workspace 접근 통제 |
| `company` | workspace_id, name, category, description, site, contact | Workspace당 기본 회사 1개 |
| `brand` | workspace_id, tone, style_rules, banned_terms, logo_asset_id | 광고 표현 규칙 |
| `offering` | workspace_id, kind(product/service), name, category, summary, status | 회사당 여러 개 |
| `audience` | workspace_id, name, situation, job, alternative | 재사용 가능한 고객군 |
| `problem` / `outcome` | workspace_id, audience_id, description | 고객 상황과 원하는 변화 분리 |
| `feature` / `benefit` | offering_id, description, benefit_text, audience_id | 기능이 누구에게 어떤 결과를 내는지 연결 |
| `claim` / `evidence` | offering_id, statement, evidence_id, source_url_or_asset, verified_at, status | 수치·비교·효능 주장은 확인된 증거와 연결 |
| `price` | offering_id, amount_text, currency, conditions, valid_from, valid_to | 가격 수정 기록·유효기간 유지 |
| `asset` | workspace_id, object_key, type, size, metadata, rights_note | 로고·사진·문서, 권한과 출처 |
| `content` / `content_version` | workspace_id, offering_id, audience_id, objective, channel, language, body, status, source_snapshot, created_by | 초안 버전과 생성 당시 원천 정보 고정 |
| `generation_run` | workspace_id, content_id, model, prompt_version, source_ids, outcome, token/cost_estimate | 사용량과 오류 추적, 비밀정보 제외 |

모든 쿼리는 서버에서 `workspace_id` 범위를 강제한다. URL의 ID만 믿지 않는다. 관계에는 동일 Workspace 제약을 둔다. 삭제는 참조되는 콘텐츠의 과거 설명을 깨지 않도록 보관 또는 비활성화 처리한다. 원본 파일은 객체 저장소에, 메타데이터는 DB에 둔다. 문서 내용 추출은 사용자가 확인할 수 있는 후보 Fact로 가져오며 자동으로 검증된 주장으로 승격시키지 않는다.

### 제품 정보 입력 화면의 순서

`기본 정보 → 누구에게 → 문제/원하는 변화 → 해결 방식 → 기능/혜택 → 증거/가격/조건 → 이미지/문서 → 검토`.

폼은 짧은 필수 질문부터 시작하고 상세 항목을 접어 둔다. 항목마다 실제 예시를 주되 예시가 실제 데이터로 저장되지 않게 한다. `저장됨/저장 중/저장 실패`를 명확히 표시한다. 누락 상태는 **필수 누락 / 권장 보강 / 준비됨**으로 구분하며 준비도 점수를 허위 정밀도로 표현하지 않는다.

## 4. 설득 구조와 생성 규칙

**기준 서사:** `Customer → Context → Problem → Cost → Desired Outcome → Solution → How → Benefits → Proof → Difference → Trust → Action`.

| 목표/형식 | 출력 순서 | P0 |
|---|---|---|
| 제품 소개 페이지 | 대상 → 문제 → 결과 → 해결 → 작동 방식 → 혜택 → 증거 → 조건/FAQ → CTA | 예 |
| SNS 게시글 | Hook → 문제 → 혜택 → 근거 → CTA | 예 |
| 영업 이메일 | 고객 상황 → 제안 → 구체적 가치 → 근거 → 다음 행동 | 예 |
| 광고 문안 | 한 가지 목표 → 핵심 혜택 → 검증 가능한 주장 → CTA | 예, 게시 제외 |
| 제안서/영상 대본 | 상황 → 문제 → 해결 → 실행 → 증거 → 조건/CTA / Hook → 문제 → 데모 → 결과 → CTA | P1 |

모든 생성 요청은 `workspace_id`, `offering_id`, `audience_id`, `objective`, `format`, `language`, `tone`, `length`, `cta`, `source_revision`을 가진다. 서버가 선택한 자료만 검색해 프롬프트에 넣는다. 출력은 구조화된 `headline`, `sections`, `cta`, `used_source_ids`, `unsupported_claims`, `missing_facts`로 받되 서버에서 검증하고 본문으로 렌더링한다.

**진실성 규칙:** 제공되지 않은 수치·평가·고객 사례·인증·가격·보증을 만들지 않는다. 비교 우위와 건강·재무 효과 등 민감한 주장은 확인된 자료가 없으면 삭제하거나 검토 요청으로 표시한다. 자료가 부족하면 사실에 충실한 짧은 결과와 보완 질문을 제시한다. AI 초안은 `draft`, 사람이 수정·승인한 것은 별도 버전이다. 외부 공개 전에 명시적으로 승인한다. AI 서비스 장애 시 입력 사실만 재구성하는 기본 생성으로 표시하거나 재시도하며, 성공한 AI 결과처럼 포장하지 않는다.

## 5. 화면 구조와 디자인 시스템

**참조 방향:** [Business X 시작 화면](https://business.x.com/en/advertising/get-started-with-twitter-ads)의 목표를 먼저 설명하는 정보 위계, 단계별 시작 안내, 분명한 CTA와 [X Ads Manager](https://business.x.com/en/help/campaign-setup/x-ads-manager)의 중앙 작업공간·필터·결과 확인 흐름을 제품에 맞게 해석한다. 이는 레이아웃 원칙의 참조이며 시각적 복제가 아니다.

### 공개 홈페이지

1. 얇고 명확한 상단 내비게이션: 제품 / 작동 방식 / 활용 사례 / 로그인 / `무료로 시작`.
2. 넉넉한 여백의 큰 제목: 고객이 얻는 결과를 1문장으로, 보조문 2줄, 기본 CTA 1개. 옆에는 **실제 앱 화면 기반** 제품 미리보기. 가짜 성과 숫자 사용 금지.
3. 목표 선택 카드: `제품을 알리기`, `고객 문의 얻기`, `영업자료 만들기`. 누르면 맞는 사용 예시/가입 흐름으로 이동.
4. `정보 입력 → 목표 선택 → 초안 제작 → 검토·저장` 4단계 섹션.
5. 지식 재사용, 근거 관리, 여러 형식의 결과 예시, 보안/데이터 통제 설명, FAQ, 마지막 CTA.

### 로그인형 앱

- **Desktop:** 왼쪽 고정 내비게이션(개요, 내 비즈니스, 제품·서비스, 고객·가치, 자산, 콘텐츠 스튜디오, 콘텐츠 보관함, 설정), 중앙 작업영역, 우측은 필요 시 미리보기/근거 패널. 상단에 Workspace 전환·검색·프로필.
- **개요:** `정보 보완하기`와 `콘텐츠 만들기` 두 행동, 최근 제품·초안·누락 증거 표시. P0에서는 실제 수집하지 않은 노출/전환 지표 카드 금지.
- **스튜디오:** 상단 목표 선택 → 제품/고객 선택 → 형식/언어 선택 → 생성. 데스크톱은 설정과 결과를 나란히, 모바일은 설정 뒤 결과를 순서대로. 결과에는 `사용한 사실`, `확인이 필요한 주장`, `원천 버전`, `편집`, `새 버전`, `복사`, `다운로드`.
- **보관함:** 목표·채널·언어·상태로 필터, 최근 수정 순서, 이전 버전 보기.
- **모바일:** 한 열, 충분한 터치 영역, 바닥에 주요 행동 고정 가능, 메뉴는 드로어. 320px에서도 가로 스크롤 없이 핵심 작업 가능.

### 시각 규칙

검정·흰색·중립 회색을 주조색으로 하고 구분이 필요한 핵심 CTA에만 고유 강조색 하나를 사용한다. 큰 헤드라인과 선명한 글꼴 위계, 얇은 경계선, 충분한 여백, 읽기 쉬운 카드와 실제 제품 이미지. 한국어와 중국어 줄바꿈을 직접 확인한다. 버튼·상태·오류는 색상 외 텍스트/아이콘으로도 구분한다. 키보드 이동, 레이블, 포커스, 대비를 갖춘다. X 로고, 상표 문구, 화면 스크린샷이나 픽셀 단위 복제는 쓰지 않는다.

## 6. 구현 방향

**기본 선택:** TypeScript 기반 반응형 웹 프런트엔드 + 서버 API + PostgreSQL + 객체 저장소 + 서버 전용 AI 제공자 어댑터. 기존 저장소의 스택이 충분하면 교체하지 않고 확장한다. 새로 시작한다면 Next.js/React, PostgreSQL, 검증된 인증 제공자를 기본으로 한다. AI 모델명, 저장소 사업자, 호스팅은 환경 설정으로 분리하고 비밀키는 서버에만 둔다.

**필수 인터페이스 예:** `GET/PUT /api/workspaces/:id/company`, `GET/POST/PUT /api/workspaces/:id/offerings`, `.../audiences`, `.../assets`, `POST .../generations`, `GET/PUT .../contents/:id`, `GET .../contents/:id/versions`. 응답은 작업공간 접근 검증, 입력 검증, 일관된 오류 코드가 선행한다. 생성 요청에는 중복 실행 방지 키, 상태(`queued/running/succeeded/failed`), 안전한 타임아웃과 재시도 처리가 필요하다.

**보호:** 인증 세션, 역할 기반 권한, DB 행 단위/동등한 서버 정책, 파일 형식·용량 검증, 비공개 다운로드 URL, 요청량 제한, 업로드 악성파일 검사 또는 격리, 생성 비용 한도, 실패·접근 기록, 백업/복원 절차. 프롬프트에 다른 고객사의 자료가 섞이지 않도록 검색·캐시·로그도 Workspace 단위로 분리한다. 자산의 사용권·출처와 AI 제공자 전송 범위를 화면에서 알 수 있게 한다. 법적 문구와 보존 기간은 실제 출시 지역이 정해질 때 검토한다.

**이전 시제품 활용:** `product-studio-mvp.zip`은 Python 단일 사용자 로컬 서버다. 이름/대상/특징/가격/문의/언어/사진을 받아 글, 정사각·세로 이미지, 9초 무음 슬라이드 영상과 SRT/ZIP을 만든다. 서버의 문구·렌더링 로직은 검토 후 P1의 미디어 작업자로 재사용 가능하다. 현재 출력 폴더와 로컬 단일 사용자 구조는 멀티테넌트 저장소나 인증을 대신할 수 없다. 첫 구현은 코드를 검사해 기능 단위로 포팅/격리하고, 기존 시제품을 인터넷에 그대로 공개하지 않는다.

## 7. 개발 순서와 승인 게이트

| 순서 | 산출물 | 완료 확인 |
|---|---|---|
| 1 | 저장소 점검, 간단 ERD, 화면 흐름, 실행 계획 | 시제품 재사용 목록·개발 방식·P0 범위가 문서화됨 |
| 2 | 디자인 토큰 + 공개/앱 주요 화면 | 데스크톱·iPhone 폭 미리보기, 실제 클릭 경로 |
| 3 | 인증, Workspace, DB, 권한, 자료 CRUD | 서로 다른 두 고객사의 자료를 상호 열람/수정할 수 없음 |
| 4 | 지식 관계·자산·가격 버전 | 정보 저장/수정/재접속 시 유지, 업로드·오류 처리 |
| 5 | 생성 엔진과 스튜디오 | 세 형식·세 언어 중 지정한 형식/언어로 결과, 근거 표시, 허위 주장 통제 |
| 6 | 편집·버전·보관·내보내기 | 가격 변경 전/후 콘텐츠 구분, 다운로드/복사 |
| 7 | 품질·운영 점검 | 수용 시나리오 통과, 설정 문서, 배포 가능한 빌드 |

P0의 **배포는 검토 가능한 미리보기**를 먼저 만든다. 외부 공개 사이트, 고객 데이터가 있는 실서비스, 외부 채널 게시, 실비가 드는 AI 서비스 활성화는 비용과 공개 범위를 제시한 뒤 별도 승인 단계로 둔다. 기존 허가가 있다면 그 범위 안에서 진행한다.

### 수용 시나리오

1. A와 B 계정으로 각각 Workspace를 만들고 A의 제품·파일·초안 URL을 B로 열어도 접근이 거절된다.
2. A는 `공원구 입문 체험`을 등록하고 한국어 제품 페이지와 중국어 SNS 글을 만든다. 출력마다 대상·CTA·사용 근거가 보인다.
3. 검증된 근거 없이 `매출 50% 증가`를 요청해도 수치를 사실처럼 쓰지 않고 보완 요청을 표시한다.
4. 가격을 바꾼 뒤 기존 초안의 이력은 보존되고 새 초안에는 새 가격이 반영된다.
5. 생성 실패나 업로드 오류는 데이터 손실 없이 다시 시도할 수 있다.
6. iPhone 화면에서 가입, 수정, 생성, 미리보기, 복사가 된다.

## 8. Work와 협업할 때의 보고 형식

매 마일스톤마다 **완료한 화면/기능, 실제 경로, 검증 방법과 결과, 남은 문제, 다음 작업**을 짧게 보고한다. 요구사항이 애매하면 이 문서의 기본값을 사용하고 해당 가정을 기록한다. 실패를 숨기지 않고 재현 방법을 적는다. 하나의 기능을 완성하기 전에 P1/P2 기능을 선행 구현하지 않는다. 화면은 플레이스홀더 숫자 대신 실제 테스트 데이터임을 분명히 표시한다.

### Work에 첫 지시로 붙여 넣을 문장

> 첨부한 `Master_Development_Specification.md`를 읽고 P0를 구현해줘. 먼저 기존 `product-studio-mvp.zip` 또는 현재 프로젝트를 검사해서 재사용 가능 기능을 정리해. 이어서 ERD와 주요 화면을 짧게 제시하고, 별도의 긴 확인 대화 없이 문서의 기본값대로 구현·테스트·미리보기까지 진행해. 단계마다 실제 동작 증거를 남기고, 로그인한 서로 다른 두 Workspace의 데이터 분리를 반드시 검증해. 외부 게시와 유료 서비스는 승인 경계를 지켜.
